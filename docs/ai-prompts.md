## Phase 3: Authentication
- **Prompt / instruction:** Run Phase 3 only, plan mode first, plan + commit list before approval. Specific requirements: `POST /register`, `POST /login`, `GET /me` (protected), `POST /logout`; bcrypt cost 12, never return/log the hash or plain password; zod validation (email trimmed/lowercased, password strength); generic "Invalid credentials" with no user-enumeration signal, including timing (compare against a dummy hash); JWT with `HS256` pinned on both sign and verify; `authenticate` (401 for missing/malformed/invalid/expired) and `authorize(...roles)` (403) middleware; duplicate email → 409 handled via the unique constraint (P2002), not just a pre-check; stricter rate limit on register/login; register hard-codes `HR_MANAGER`, role not client-choosable; stateless logout, `tokenVersion` only if it stays small, documented; a specific list of required tests including hash-never-plaintext, duplicate email, validation failures, login success/failure, missing/invalid/expired/tampered/wrong-algorithm tokens, VIEWER 403, response never contains `passwordHash`, and a logging-redaction check.
- **What the AI proposed:** A plan (approved before code) as 7 commits: password/JWT lib helpers, `authenticate`+`authorize` middleware (tested against a small purpose-built route since no real write route exists until Phase 4), the auth module's schema/repository/service layer, the controller+routes+app wiring, an auth-specific logging-redaction regression test, an integration test suite against real Postgres, and a docs commit. Key calls stated up front: `bcryptjs` over native `bcrypt` (no native compile step), JWT payload kept to `{ sub, role }` with no DB read in `authenticate` (only `/me` does a lookup, for `name`/`email`), `.strict()` zod schemas plus a hard-coded role in the repository as two independent layers against a client-chosen role, and `/logout` made `authenticate`-protected (spec only marked `/me` as protected, logout was my own judgment call).
- **What I changed or rejected, and why:** Approved the plan as proposed, no changes during implementation — Phase 2's cross-cutting pieces (error taxonomy, validation middleware, rate limiter factory, config) were already exactly what auth needed, so this phase had no real surprises. One digression before Phase 3 started: fixed `PROJECT_SPEC.md`/`CLAUDE.md` to reflect Phase 2's `prisma/` relocation into `apps/api/`, per explicit instruction.
- **Outcome:** All 7 planned commits landed. `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test` pass across all packages (92 API tests). `pnpm test:integration` passes against real Postgres (7 new auth tests: register, duplicate email, login success/failure, `/me`, `/logout`). Manually curl-verified the full flow against a running server — register → login (success, wrong password, unknown email — the latter two producing byte-identical bodies) → `/me` with/without a token → `/logout` → duplicate registration (409) — and grepped the server's log output for the plaintext passwords used in the requests: no matches.

## Phase 4: Employees module
- **Prompt / instruction:** Run Phase 4 only, plan mode first. Employees endpoints under `/api/v1/employees`, all behind `authenticate`, reads open to any role, POST/PUT/DELETE `authorize('HR_MANAGER')`. List with `page`/`pageSize` (default 25, max 100), `search`, `country`/`department`/`jobTitle` filters, whitelisted `sortBy`/`sortDir` with an `id` tiebreaker, and `meta { page, pageSize, total, totalPages }`. Strict zod validation (ISO country/currency, salary bounds, hireDate not in the future, UUID params), 409 via P2002, 404, 204 on delete. A streaming, filter-aware CSV export declared before `/:id`, with formula-injection neutralization. Audit the indexes, decide on `pg_trgm`, and test everything listed. Later, because a long response was blocked by the content filter, the work was re-split into five small steps (schema+repository, service+list, controller+routes, tests, CSV export), each committed separately.
- **What the AI proposed:** A 7-commit plan (approved before code). During implementation it deviated from the plan in one place: ISO country and currency validation uses `i18n-iso-countries` and Node's `Intl.supportedValuesOf('currency')` instead of hand-written code lists in `packages/shared`, which avoids lists that drift. The Node/ICU dependence of the currency list is recorded as a trade-off.
- **What I changed or rejected, and why:** Approved as proposed, then the step split and the ISO-library change above. Two implementation calls worth noting: `department`/`jobTitle` filters are exact and case-sensitive so their indexes stay usable, and the export handler fetches its first batch before sending headers (so an early DB error is still a JSON envelope) while an error handler guard drops the connection if a failure happens mid-stream. One commit (`8d03fc5`, a `tsconfig.json` tweak) was made outside this work and left as is. Also fixed an earlier mistake in the process: my `pkill -f` was matching its own shell, so stale dev servers were killed by PID instead.
- **Outcome:** Five feature/test commits plus this docs commit. `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test` pass (138 API unit tests). The integration suite (69 tests, 45+15 for employees) passes against real Postgres. `EXPLAIN ANALYZE` on 10,000 synthetic rows confirmed the existing indexes are used for the `country`/`department` filters and `salary` sort, and found `search`, and sorting on `fullName`/`email`/`hireDate`/`createdAt`, unindexed but fast (8.2 ms worst case), so no new migration and no `pg_trgm`. A full export of 10,000 rows streamed in about 270 ms. Findings and the performance rows are in `docs/design-notes.md`; re-measure against the real seed in Phase 5.
