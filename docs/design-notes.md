# Design notes

Trade-offs, alternatives considered, and performance measurements. Update as decisions are made.

## Decisions
| Decision | Options considered | Choice | Reason |
| -------- | ------------------ | ------ | ------ |
| `packages/ui` | Shared UI primitives package vs. web-only `components/ui` | Omitted (web-only `components/ui`) | Only one consumer (`apps/web`) exists in this project; a shared package would add a build/publish step for zero reuse benefit. Spec §3 explicitly allows skipping it. |
| `db:*` root scripts | Add `db:migrate`/`db:seed`/`db:reset` in Phase 1 vs. defer | Deferred to Phase 2 | Prisma doesn't exist until Phase 2 (spec §12); a script that always fails until then is worse than no script. |
| `apps/api` Phase 1 scope | Build health check / config / error handling now vs. bare scaffold | Bare `createApp()` factory (Express + JSON body parsing only) | Spec §12 assigns config validation, Prisma, error handling, logging, and the health check to Phase 2. Building them now would violate "work one phase at a time" and get redone once real config validation lands. |
| Pre-commit linting | `eslint --fix` + `prettier --write` in lint-staged vs. `prettier --write` only | Prettier only | Each workspace package owns its own flat `eslint.config.js`; `eslint --fix` invoked from the repo root (where lint-staged runs) can't resolve per-package configs. `pnpm lint` (via Turborepo, per-package) remains the enforced gate before every commit per `CLAUDE.md` rule 3. |
| `eslint-plugin-import`'s `import/named` rule | Keep vs. disable | Disabled | It flags false positives on named imports from ESM-only packages (`@tanstack/react-query`, `@testing-library/react`) because its resolver isn't configured for workspace/path resolution. TypeScript's own type checking already catches genuinely missing exports, so the rule was redundant as well as noisy. |
| Root `tsconfig.json` | Full compiler options vs. references-only solution file | References-only (`"files": []` + `references`) | Actual strict compiler options live in `packages/typescript-config` and are consumed per-package; the root file exists only for spec §3 structure compliance and editor cross-package navigation — no script invokes `tsc -b` at the root. |
| `prisma/` location | Repo root (spec §3's tree) vs. inside `apps/api` | Inside `apps/api` (`apps/api/prisma/`) | Prisma's client generator infers its own "project root" — and where it self-heals by running `pnpm add @prisma/client -D --silent` when it can't resolve the package — from the schema file's own directory, not from the invoking CWD, `--schema`, or even a `prisma.config.ts` placed elsewhere. With the schema at the repo root and `@prisma/client` deliberately installed only in `apps/api` (to avoid pnpm's non-hoisted node_modules resolution issues across workspace packages), every `prisma generate` attempted that self-heal at the workspace root, which pnpm blocks without `-w`. Co-locating `prisma/` with its only consumer is standard practice for exactly this reason and was empirically confirmed to fully resolve it — a real, reproducible tool/monorepo interaction, not a stylistic preference. |
| `db:seed` / `db:reset` root scripts | Add now (as originally planned for "Phase 2 adds all three `db:*` scripts") vs. defer further | Deferred to Phase 5 | `db:migrate` and `db:generate` are genuinely useful today and were added. `db:seed`/`db:reset` only make sense once `prisma/seed.ts` exists (spec §12 assigns seeding to Phase 5); a `db:reset` that runs a nonexistent seed script would either error or silently skip, which is worse than not having the script yet. |
| Error handler response sanitization | Branch on `NODE_ENV` (spec's literal "never expose... in production") vs. always sanitize | Always sanitize (every environment) | `classifyError()` already produces a safe `message` for every error, operational or not; branching in the handler to show raw details outside production would duplicate that logic for a marginal dev-convenience benefit. Full detail (message + stack) is always one line away in the structured logs (pino-pretty in non-production), so nothing is lost — just never sent over HTTP, in any environment. Stricter than the spec requires, and simpler. |
| `ApplicationLog` async writes | Buffered/batched queue vs. one fire-and-forget write per log call | Fire-and-forget per call | Spec §10.4 explicitly allows either "a small in-process buffer or batch." At this project's expected local/demo traffic, a batching queue adds real complexity (flush timers, backpressure, partial-batch failure handling) for no measurable benefit. Documented here as the point where a real queue/worker (e.g. a small in-memory ring buffer flushed on an interval, or offloading to a proper queue) would become worth it: once log volume is high enough that per-call `prisma.applicationLog.create()` round-trips start competing with request-serving connections for the pool. |
| Validation error response shape | Add a `details`/`errors` field with per-field issues vs. a single joined `message` | Single joined `message` string | The spec's documented error envelope is exactly `{ success, message, code, requestId }` with no extra field shown for validation errors specifically. `validate()` joins zod's issues into one readable string instead, keeping every error response — validation or otherwise — inside the one documented shape rather than growing an undocumented, validation-only extra field. |
| Rate limiting scope | Apply a single global limiter now vs. wait for per-route limiters | One global limiter (`createRateLimiter()`, 300 req/15 min by default) applied in `app.ts` | Spec asks for rate limiting to be "stricter on auth routes," but no auth routes exist yet (Phase 3). A global limiter is real, tested protection today; a second, stricter instance scoped to `/auth/*` is a one-line addition once those routes land, not a redesign. The "Security" checklist box in `README.md` stays unticked until that auth-specific half exists, since it bundles both into one item. |
| Password hashing library | Native `bcrypt` vs. `bcryptjs` | `bcryptjs` | Same algorithm and cost factor (12); `bcryptjs` is pure JS with no native addon to compile, removing a class of CI/Docker-image build failures. The measurable cost: hashing takes ~400-600ms in this environment instead of native bcrypt's usual ~50-100ms, which only matters on the register/login hot path, not at rest. Acceptable at this project's scale; would reconsider under real production auth traffic. |
| JWT revocation / logout | Add a `tokenVersion` column on `User` (checked on every `authenticate` call) vs. stay fully stateless | Fully stateless — no `tokenVersion`, no denylist | Spec §7 explicitly allows this ("implement `tokenVersion` only if it stays small"). A `tokenVersion` check means either a DB read on *every* authenticated request (defeating the point of a stateless JWT) or an in-memory/Redis cache layer (real infrastructure this project doesn't otherwise need). `POST /auth/logout` exists and is `authenticate`-protected for API completeness and to give the client an explicit signal to discard its token, but does nothing server-side. Bounded by the short default `JWT_EXPIRES_IN` (1h). What a real revocation strategy would add later: a `tokenVersion` int on `User`, incremented on logout-all or password change, embedded in the JWT payload and compared against the DB value in `authenticate` — at the cost of a DB read per request, or a cache with its own invalidation problem. |
| `authenticate` and `/me` data source | Re-fetch the user from the DB on every authenticated request vs. trust the JWT payload | Trust the JWT payload (`{ sub, role }`) in `authenticate`; only `GET /me` does a `findUserById` lookup, since it's the only endpoint that needs `name`/`email` | Keeps the JWT payload minimal and `authenticate` fast and DB-free — the actual point of using a stateless JWT instead of a session lookup. Trade-off: a token stays valid (in the sense of passing `authenticate`) even if the underlying user is deleted, until it expires; `/me`'s own lookup catches that specific case (responds 401, not 404, so a deleted user's id isn't distinguishable from a garbage id) but no other route would today. Acceptable for a 1h-lived token at this project's scope. |
| `POST /auth/logout` protection | Public vs. `authenticate`-protected | `authenticate`-protected | Spec only explicitly marks `GET /me` as "(protected)"; logout isn't specified either way. Requiring a valid token to log out matches the general shape of the other protected/unprotected split (you can only log out of a session you're actually in) and costs nothing extra since the endpoint is otherwise a no-op. |
| Login timing-safety | Short-circuit on unknown email vs. always run a password comparison | Always compare — against the real hash if the user exists, against a fixed dummy hash (computed once at module load) otherwise | A `findUserByEmail` miss that skips straight to a 401 is measurably faster than a hit that also runs a ~500ms bcrypt compare, which is itself a user-enumeration side channel via response timing. Comparing against a dummy hash either way keeps both paths' cost dominated by the same bcrypt operation. The dummy hash is computed once per process (top-level `await` in `auth.service.ts`), not per request. |
| ISO country/currency validation | Hand-maintained code lists in `packages/shared` vs. libraries | `i18n-iso-countries` for ISO 3166-1 alpha-2, Node's built-in `Intl.supportedValuesOf('currency')` for ISO 4217 | No list to drift out of date or mistype. Trade-off: the currency list follows the Node/ICU version the process runs on, so a very new or retired code can differ between Node versions; only loosely constrained here (`engines` says Node >= 20); a whitelist copy would be the fix if that ever mattered. Both are format-checked (2 vs. 3 uppercase letters) before the lookup. |
| Salary bounds | No cap vs. a sane cap | Integer minor units, 0 to 2,000,000,000 | Prisma `Int` is Postgres `INTEGER` (max 2,147,483,647); the cap stays under it so a valid-looking value can never fail at the column. Zod is the only upper bound (the DB `CHECK` only enforces `>= 0`). |
| `PUT /employees/:id` | Full replace vs. partial update | Full replace (same schema as create) | Matches PUT semantics and needs one schema, not two. |
| List pagination | Offset (`skip`/`take`) vs. keyset | Offset for the list; keyset for the CSV export | The list has a page-number contract and skipping up to ~10k rows is cheap. The export has no page number and walks every row, so it uses a cursor. Both always sort by the chosen column then `id`, so pages never overlap or skip rows (tested with all-tied sort keys). |
| `pageSize` over the max | Reject with 400 vs. clamp | Clamp to 100 | "Hard max" is treated as a ceiling. A `page` past the end is a normal empty result with accurate totals, not an error. |
| `department` / `jobTitle` filters | Case-insensitive vs. exact | Exact, case-sensitive; only `search` is case-insensitive | A case-insensitive match (`ILIKE`/`lower()`) cannot use the btree indexes on those columns. The UI should send stored values (e.g. from a dropdown). |
| Search index | `pg_trgm` GIN index vs. sequential scan | No index; `ILIKE '%term%'` on `fullName` and `email` via a sequential scan | Measured on the real 10,000-row seed: 8.5 ms of execution (see the audit below). A plain btree can't serve a leading-wildcard `ILIKE`, and `pg_trgm` adds a `CREATE EXTENSION` deployment dependency (not on every managed Postgres tier) for a gain that only matters at a much larger scale. Revisit if search latency becomes visible or the table passes roughly 100k rows. |
| List index audit | Add indexes vs. leave as is | No new migration | `EXPLAIN ANALYZE` on the real 10,000-row seed (local Docker Postgres 16, `ANALYZE`d): `country` filters use `Employee_country_idx`; `department` uses `Employee_department_idx`; sorting by `salary` uses `Employee_salary_idx`. For `country + jobTitle` sorted by salary the planner scanned the salary index backwards and filtered (removed 3,142 rows to find 25, about 1 ms), which is fine here but is where a `(country, jobTitle, salary)` index would help at larger scale. Not covered by any index: sorting by `fullName`, `email`, `hireDate`, `createdAt` (top-N heapsort over a sequential scan, 1.1 ms for `hireDate`) and `search`. All acceptable at 10k rows. (An earlier check on uniform synthetic data made the planner pick the composite `(country, jobTitle)` index for country filters and suggested the standalone `country` index was redundant. That was an artefact of the synthetic distribution: on the real seed the standalone index is the one used, so it stays.) |
| CSV export streaming | Load all rows vs. batches | Async generator paging with a keyset cursor, 500 rows per batch, written to the response with backpressure | One batch in memory at a time (Prisma has no server-side streaming cursor, so batches are the practical form). Batches are not one snapshot: concurrent writes during a long export can be missed or repeated; acceptable for this project. The first batch is fetched before headers are sent so an early database failure is still a normal JSON error; a failure mid-stream drops the connection (logged) since a JSON body can no longer be sent. |
| CSV salary column | Convert to major units vs. export as stored | Exported as stored, in minor units, with `currency` in the adjacent column | Decimal places differ by currency (JPY 0, most 2, some 3), so a correct conversion needs a per-currency exponent table; exporting raw integers next to the currency code is exact and unambiguous. Cost: HR sees `9000000` for 90,000.00, so a formatted export (or a "major units" option) is a sensible follow-up. |
| CSV cell safety and encoding | Escape only vs. also neutralize formulas | RFC 4180 quoting (CRLF rows) plus a leading `'` on any cell starting with `=`, `+`, `-`, `@`, tab or carriage return | The leading apostrophe is the usual defence against cells being read as formulas in Excel/Sheets; neutralizing happens before quoting. Known limitation: no UTF-8 BOM, so Excel may misread non-ASCII names when opening the file directly (importing as UTF-8 works). |
| Seed code location | `apps/api/prisma/seed.ts` (spec tree) vs. `apps/api/src/seed/` | `apps/api/src/seed/`, run with `tsx src/seed/run.ts` via `pnpm db:seed` | `tsconfig` only compiles `src/`, so the generator is type-checked, linted and unit-tested with the rest of the API. Prisma's own seed hook isn't used, so nothing depends on Prisma's config-file conventions. |
| Seed determinism | Random data each run vs. seeded | mulberry32 PRNG with a fixed seed; ids are drawn from the same stream (UUID-shaped); hire dates are computed against a fixed reference date (2026-06-30), not `Date.now()` | Two runs produce byte-identical rows, so demos, bookmarks and tests are stable, and no hire date is ever in the future. Cost: the data doesn't age (tenure is "as of 2026-06-30"). Every row consumes the same number of random draws, so the first N rows don't depend on the total count. |
| Seed data model | Uniform random vs. structured | 9 countries with matching currencies (US, GB, DE, FR, IN, JP, BR, CA, AU); 18 titles with departments and USD bands; band x country cost factor x static approximate USD rate, converted with the ICU minor-unit exponent (JPY 0, others 2) and rounded to 3 significant figures; tenure uplift 1.5% per year (cap 15); part-time 0.6x, contract 1.1x, intern 0.35x (interns only on eligible titles); about 1% deliberate outliers at 1.8x or 0.55x | Gives Phase 6 real signal (per-country pay, pay-vs-tenure trend, outliers to detect). The rate table is static and approximate (`APPROXIMATE_USD_RATES` in `packages/shared`, reused by the optional USD view), never fetched. Real seeded salaries top out well under the integer cap (asserted in a test using the worst-case multipliers). Limitation: small name pools mean repeated names; emails stay unique via a numeric suffix. |
| Seed write strategy | Row-by-row upserts vs. delete + `createMany` | One interactive transaction (120 s timeout, default is 5 s): delete all employees, `createMany` in batches of 1,000, verify the stored count equals the generated count, upsert the demo users | All-or-nothing: a failure leaves the previous data instead of an empty table. Only `Employee` rows are deleted; other users and `ApplicationLog` rows are untouched. About 1.3 s for 10,000 rows (3.2 s wall including startup and one bcrypt hash). |
| Demo accounts | One HR user vs. HR + Viewer; password handling | Two labelled demo accounts (`hr.demo@acme.example` HR_MANAGER, `viewer.demo@acme.example` VIEWER), same public documented password, overridable with `DEMO_USER_PASSWORD`; role set by the seed itself | Lets a reviewer try both roles immediately. The password is public by design (it's in the README), so deployed environments should override it. Not validated against the registration password rules; an override is trusted. |
| Seed safety | Always allowed vs. guarded | Refuses when `NODE_ENV=production` unless `ALLOW_PRODUCTION_SEED=true`; `db:reset` runs the same check before it drops anything | The seed deletes every employee; a stray run against a production URL must not do that silently. Phase 10 has to seed production on purpose, hence an explicit opt-in rather than a hard block. `db:reset` wraps `prisma migrate reset --force`, which drops the database; it was not run during this phase (only the guard script and `db:seed` were), so run it once by hand on a throwaway database before relying on it. |
| Node version | Node 24 LTS vs. Node 26 | Node 24 (Active LTS "Krypton", 24.21.0), pinned in `.nvmrc` (which CI reads), root `engines` and `@types/node` | Checked on nodejs.org on 2026-09-30: 24 is Active LTS and 26 is still "Current". `CLAUDE.md` describes 24 as "Current, enters LTS in October 2026", which is really 26's status; the number in the file (24) was followed and the wording flagged. Dockerfiles don't exist yet, so Phase 10 must pin the same version. |
| pnpm 12 supply-chain policy | Relax `minimumReleaseAge` vs. re-resolve | Kept the default policy, regenerated the lockfile | pnpm 12 rejected two transitive versions published within the last day. A fresh resolution picked in-policy versions; loosening a security default to make an old lockfile pass was the wrong way round. Build scripts are approved by name in `pnpm-workspace.yaml` (`allowBuilds`: `@prisma/client`, `@prisma/engines`, `prisma`, `esbuild`). |
| Express 5 | Stay on 4 vs. upgrade | Express 5.2.1 | Two real behaviour changes surfaced and were fixed: `req.query` is a read-only getter (so `validate()` shadows it with an own property), and `app.listen` reports startup failures through its callback (so `server.ts` now logs a fatal error and exits 1 instead of claiming to have started). |
| Zod 4 deprecated helpers | Migrate to `z.email()`/`z.uuid()`/`z.strictObject()` vs. keep | Kept `.email()`, `.uuid()`, `.strict()` | They still work. Moving the string ones would change check order (format check before `.trim()`/`.toLowerCase()`), which would reject padded emails; tests guard that. Revisit when zod removes them. |
| Prisma 7 client | Keep `prisma-client-js` vs. new `prisma-client` generator | New `prisma-client` generator, output `apps/api/src/generated/prisma` (git-, eslint-, prettier-ignored, generated on install), `@prisma/adapter-pg` driver adapter with a 5 s connection timeout, URL in `apps/api/prisma.config.ts` | The old provider is deprecated in v7. pg has no connection timeout by default (v6 used 5 s), and without one a health check against an unreachable database would hang. `prisma generate` reads the URL tolerantly so a fresh clone can install before `.env` exists. Seeding 10,000 rows takes 2.4 s now versus 1.3 s on Prisma 6 (adapter overhead), still fine. |
| Held back: TypeScript 6.0.3 | 7.0.2 (latest) vs. 6.0.3 | 6.0.3 | `typescript-eslint` declares `typescript >=4.8.4 <6.1.0`; 7 would break linting. |
| Held back: ESLint 9.x | 10.11.0 (latest) vs. 9.x | 9.39.5 (pnpm flags it deprecated) | `eslint-plugin-react`, `eslint-plugin-import` and `eslint-plugin-jsx-a11y` declare no ESLint 10 support. Revisit when they do. |
| Held back: Tailwind 3.4 | 4.3.3 vs. 3.4 | 3.4.19 | `CLAUDE.md` allows v3 as long as a `tailwind.config.js` theme stays; v4 would rewrite the design-system stylesheet just before the UI phases build on it. |
| `@types/node` | 26 (latest) vs. matching the runtime | `^24` | Types should describe the Node the code runs on, and that's 24. |

**Found during the upgrade, not caused by it (open):** `pnpm build` followed by `node dist/server.js` does not start. `@payscope/shared` is consumed as TypeScript source (`"main": "./src/index.ts"`), and its imports use `.js` specifiers (`./fx-rates.js`) that only resolve when a tool like `tsx` or Vitest maps them to the `.ts` files; plain Node fails with `ERR_MODULE_NOT_FOUND`. It has been broken since Phase 4 first imported runtime code from `shared`; `tsx` (dev), Vitest and the integration tests all transpile it and hide the problem. Fix before Phase 10 (deployment): either build `shared`/`types` to `dist` and point `main`/`exports` there, or bundle the API for production.

## Test consolidation (change request B)

All tests live in the root `tests/` workspace package (`@payscope/tests`), mirroring source paths. Nothing test-related remains in `apps/*` or `packages/*`; `scripts/check-test-locations.mjs` (chained into `pnpm lint`, so CI's Lint step runs it) fails on any `*.test.*` / `*.spec.*` file or `__tests__` folder outside `tests/`.

| Decision | Options considered | Choice | Reason |
| -------- | ------------------ | ------ | ------ |
| Reaching source from tests | Deep relative paths vs. path aliases vs. building packages first | Aliases `@api/*`, `@web/*`, `@shared/*`, `@shared-types/*` (tsconfig `paths` and Vitest `resolve.alias`) | Short stable imports; `vi.mock` uses the same specifier, so it matches the module the source loads. No build step before tests. |
| Third-party resolution | Give `tests` every dependency the source uses vs. only what test files import | Only what test files import, at the same versions as the apps | Imports inside source files resolve from that file's own package, so the API still uses its own `express`, `pg`, `@prisma/*`. Matching versions keeps one copy of React and Express in the store; the web project also sets `resolve.dedupe` for React. |
| Prisma 7 client, adapter, config | Add Prisma to `tests` and regenerate vs. reuse the API's | Reuse. `tests` has no Prisma dependency and never imports `@prisma/client` | Tests reach the client through `@api/database/prisma.js`, so the generated client (`apps/api/src/generated/prisma`, made by `prisma generate` on install), `@prisma/adapter-pg` and `pg` all resolve from `apps/api`: one client, one adapter. Migrations run in global setup with `pnpm exec prisma migrate deploy` and `cwd: apps/api`, so `prisma.config.ts`, the schema and migrations are found exactly as when the suite lived there. |
| Vitest layout | Per-package configs vs. one config with projects | One `tests/vitest.config.ts` with `api-unit`, `api-integration`, `web`, `packages` projects | `pnpm test` runs `api-unit`, `web` and `packages`; `pnpm test:integration` runs `api-integration` (serial files, truncate after each test). `web` keeps `globals: true` because Testing Library's automatic cleanup needs a global `afterEach`. |
| Type checking tests | Separate tsconfigs per area vs. one | One `tests/tsconfig.json` (Bundler resolution, DOM lib) that also includes `apps/api/src/types/*.d.ts` | The API's `Request.user` / `requestId` augmentation must be visible to tests that import the app. `rootDir` is the repo root because the program includes source outside `tests/`. |
| Turbo caching | Default task inputs vs. explicit inputs | `@payscope/tests#test` and `#typecheck` also hash `apps/*/src`, `packages/*/src` and `apps/api/prisma` | Tests no longer sit inside the package they cover, so the default key would replay a stale green after a source-only change. `test:integration` is uncached. |
| Layout | Follow the `CLAUDE.md` list only vs. mirror source exactly | Mirror source, so `api/unit/app`, `api/unit/seed`, `api/integration/app`, `api/integration/seed` and `modules/*` folders exist too | Keeps "the path tells you what is under test" true. The `.integration` file infix was dropped because the folder says it. |
| Scope of the move | Move and tidy (shared builders, dedupe) vs. pure move | Pure move | Behaviour and counts stay provably identical. Extracting shared factories into `tests/helpers` and `tests/factories` (scaffolded, empty) is a separate cleanup. |

Verification: Vitest JSON reporter snapshots of every test's file and full name before the move and after it match exactly: 188 unit (API 178, web 2, shared 6, types 2) and 76 integration tests.

## Role-aware auth and data (change request C)

| Decision | Options considered | Choice | Reason |
| -------- | ------------------ | ------ | ------ |
| Who picks the role at registration | Server decides (always VIEWER) vs. client chooses from a fixed set | Client may send `role` (`HR_MANAGER` or `VIEWER`), default `VIEWER` when omitted | Assessment-only simplification so a reviewer can try both experiences without an admin. It means anyone can make themselves an HR Manager, which a real product must not allow. Production alternative: HR Managers invite Viewers (the invite fixes the role), or new HR Manager accounts need admin approval and self-registration only ever creates a VIEWER. |
| Invalid role input | Coerce or ignore vs. reject | 400 for an unknown value, a different case, `null`, or any other extra field (schema stays `.strict()`) | A typo must never silently produce a different privilege level. |
| DB default for `User.role` | Keep `HR_MANAGER` vs. `VIEWER` | `VIEWER` (own migration) | Registration and the seed pass explicit roles (both demo users), so nothing depends on the default; if a future code path forgets the role it now gets least privilege. |
| Where salary is filtered | Controller, repository, UI, or service | Service, through one serializer | Every service function takes the caller's role and returns wire shapes, so a controller cannot receive a raw row. The response types (`EmployeeFull`, `EmployeeDirectory` in `@payscope/types`) differ, so returning the wrong one is a compile error. |
| How the VIEWER shape is built | Delete `salary` from the row vs. explicit allowlist | Explicit allowlist of fields, and an `hrOnly` flag on export columns | A column added to the model later stays hidden from VIEWERs until someone lists it. The directory shape has no `salary` key at all (not null). Any role other than exactly `HR_MANAGER` gets it, so an unexpected value in a token fails closed. |
| Sorting by salary | Allow (order only) vs. reject for VIEWER | Reject with 400 on list and export | A list sorted by salary reveals the ranking even without the numbers. There is no salary filter today (the strict query schema already rejects unknown fields); a future one must be added to `assertQueryAllowed`. |
| Auth router construction | Module-level router vs. one per app | One per `createApp()` (as the app-wide limiter already was) | The register/login limiter (10 per 15 minutes) was shared across every app in a test file, so the role tests hit 429. Each app now has its own counter. |
| Test tokens | Register through the API vs. hand-sign | Hand-signed in `tests/helpers/tokens.ts`, plus a few tests that use real registered users | `authenticate` trusts the signed payload, so signing is fast and needs no DB row; the real-user tests prove the same behavior end to end. |

## Insights (Phase 6)

Five read-only endpoints under `/api/v1/insights` (`stats`, `headcount`, `salary-bands`, `tenure`, `outliers`), all JWT-protected. Aggregates are open to both roles; `outliers` is HR only.

| Decision | Options considered | Choice | Reason |
| -------- | ------------------ | ------ | ------ |
| Aggregation | Prisma `groupBy` plus JS percentiles vs. SQL | Parameterised `$queryRaw` with `percentile_cont` | Postgres computes quartiles exactly and in one pass; 10,000 rows aggregate in about 10 ms. Values are always bound parameters; the only interpolated fragments are identifiers chosen from a whitelist by key. Counts are cast to `int` and money to `float8` (rounded in JS), so there is no BigInt and no int4 overflow of USD cents. |
| Currencies | Group by key only vs. key and currency | Always key **and** currency in the native view | Never mixes currencies silently. EUR is shared by DE and FR, so by job title they merge into one EUR row, while by country they stay separate. `groupBy=org` (currencies mixed) is only allowed in the USD view. |
| USD view | Convert in JS vs. in SQL | In SQL: the static rate table goes in as bound arrays, joined as a CTE, using each currency's minor-unit digits (JPY has none) | Percentiles must be computed over converted values, not converted afterwards. Results are US cents and labelled `approximate: true`. Employees whose currency has no rate are counted in `excludedHeadcount` instead of dropped silently. |
| What a VIEWER may see | Everything aggregated vs. suppress small groups | Groups (and salary-band sets) under 5 people are suppressed for a VIEWER, with a count of what was hidden | The statistics of a group of one are that person's salary. `CLAUDE.md` says "aggregated statistics only"; this closes the small-group hole. It is one constant and one function (`insights.access.ts`), applied to stats, salary bands and tenure. Known residual risk: min and max of a visible group are individual values (unattributed), and a bucket with a single person is coarse. HR sees everything. |
| Outliers | Fixed percentage from the median vs. a data-driven rule | Tukey fences (Q1 - 1.5 IQR, Q3 + 1.5 IQR) within `(country, currency, jobTitle)`, groups of at least 8 | No magic threshold, adapts to each group's spread, and never compares across currencies. Group statistics use the whole group; filters only narrow the list. HR only (403 for a VIEWER, before parameter validation), checked again in the service. |
| Tenure clock | Database `NOW()` vs. a date from the service | The service passes today's date as a parameter | Query results do not depend on the database clock. Tests use hire dates relative to today with months of margin around each band edge. |
| Headcount | Suppress small groups too vs. not | Not suppressed | It carries no salary data, so every role sees every group. |

**Measured on the 10,000-employee seed** (local Docker Postgres 16, HTTP time over 3 warm runs on localhost, HR account): stats by country 8 ms, by job title 9 ms (144 rows, 22 KB), by department 9 ms, org-wide USD 8 ms, country in USD 11 ms; headcount 6 ms; salary bands 5 ms (INR) and 10 ms (USD); tenure 11 ms and 13 ms (USD); outliers (limit 100) 15 ms. `EXPLAIN ANALYZE`: stats by country 10 ms (sequential scan and sort of 10,000 rows), outliers 27 ms. No new index is warranted at this size, so none was added.

**Outliers on the seed, and a trade-off to decide.** The seed injects about 1% deliberate outliers (0.5% at 1.8x, 0.5% at 0.55x). With the specified baseline (job title within a country, employment types mixed) the endpoint flags **483** employees (4.8%), and **195 of the 211 interns** (92%), because intern pay is deliberately lower than the title's median; 69 of the top 100 are interns. Grouping like-for-like by employment type as well flags **176** employees across 233 groups, much closer to the injected rate. The current build keeps the spec's baseline, and `employmentType` is in every row so HR can judge. Refining the baseline is a small follow-up if you want it.
