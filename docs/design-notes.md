## Architecture

The repo is a pnpm and Turborepo monorepo. `apps/web` (React) and `apps/api` (Express) never import each other; they share code only through `packages/shared` (zod schemas, constants, money and band helpers) and `packages/types` (API shapes). All tests live in the root `tests/` package. The API is layered: routes, thin controllers, services (business rules, role-based shaping), repositories (Prisma and raw SQL). Every response uses one envelope with a `requestId`. Diagrams: [architecture.md](architecture.md).

### Structure and tooling
| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| `packages/ui` | Omitted (web-only `components/ui`) | Shared UI primitives package vs. web-only `components/ui` | Only one consumer (`apps/web`) exists in this project; a shared package would add a build/publish step for zero reuse benefit. Spec §3 explicitly allows skipping it. |
| Root `tsconfig.json` | References-only (`"files": []` + `references`) | Full compiler options vs. references-only solution file | Actual strict compiler options live in `packages/typescript-config` and are consumed per-package; the root file exists only for spec §3 structure compliance and editor cross-package navigation — no script invokes `tsc -b` at the root. |
| `prisma/` location | Inside `apps/api` (`apps/api/prisma/`) | Repo root (spec §3's tree) vs. inside `apps/api` | Prisma's client generator infers its own "project root" — and where it self-heals by running `pnpm add @prisma/client -D --silent` when it can't resolve the package — from the schema file's own directory, not from the invoking CWD, `--schema`, or even a `prisma.config.ts` placed elsewhere. With the schema at the repo root and `@prisma/client` deliberately installed only in `apps/api` (to avoid pnpm's non-hoisted node_modules resolution issues across workspace packages), every `prisma generate` attempted that self-heal at the workspace root, which pnpm blocks without `-w`. Co-locating `prisma/` with its only consumer is standard practice for exactly this reason and was empirically confirmed to fully resolve it — a real, reproducible tool/monorepo interaction, not a stylistic preference. |

**Dev scripts.** The `db:migrate`, `db:generate`, `db:seed` and `db:reset` root scripts were added when the things they run existed (migrations in Phase 2, the seed in Phase 5), because a script that always fails is worse than none. `pnpm db:reset` drops the database and was written but deliberately never run against real data.

### Employees API and CSV export
| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| `PUT /employees/:id` | Full replace (same schema as create) | Full replace vs. partial update | Matches PUT semantics and needs one schema, not two. |
| List pagination | Offset for the list; keyset for the CSV export | Offset (`skip`/`take`) vs. keyset | The list has a page-number contract and skipping up to ~10k rows is cheap. The export has no page number and walks every row, so it uses a cursor. Both always sort by the chosen column then `id`, so pages never overlap or skip rows (tested with all-tied sort keys). |
| `pageSize` over the max | Clamp to 100 | Reject with 400 vs. clamp | "Hard max" is treated as a ceiling. A `page` past the end is a normal empty result with accurate totals, not an error. |
| `department` / `jobTitle` filters | Exact, case-sensitive; only `search` is case-insensitive | Case-insensitive vs. exact | A case-insensitive match (`ILIKE`/`lower()`) cannot use the btree indexes on those columns. The UI should send stored values (e.g. from a dropdown). |
| CSV export streaming | Async generator paging with a keyset cursor, 500 rows per batch, written to the response with backpressure | Load all rows vs. batches | One batch in memory at a time (Prisma has no server-side streaming cursor, so batches are the practical form). Batches are not one snapshot: concurrent writes during a long export can be missed or repeated; acceptable for this project. The first batch is fetched before headers are sent so an early database failure is still a normal JSON error; a failure mid-stream drops the connection (logged) since a JSON body can no longer be sent. |
| CSV salary column | Exported as stored, in minor units, with `currency` in the adjacent column | Convert to major units vs. export as stored | Decimal places differ by currency (JPY 0, most 2, some 3), so a correct conversion needs a per-currency exponent table; exporting raw integers next to the currency code is exact and unambiguous. Cost: HR sees `9000000` for 90,000.00, so a formatted export (or a "major units" option) is a sensible follow-up. |
| CSV cell safety and encoding | RFC 4180 quoting (CRLF rows) plus a leading `'` on any cell starting with `=`, `+`, `-`, `@`, tab or carriage return | Escape only vs. also neutralize formulas | The leading apostrophe is the usual defence against cells being read as formulas in Excel/Sheets; neutralizing happens before quoting. Known limitation: no UTF-8 BOM, so Excel may misread non-ASCII names when opening the file directly (importing as UTF-8 works). |
| Salary bounds | Integer minor units, 0 to 2,000,000,000 | No cap vs. a sane cap | Prisma `Int` is Postgres `INTEGER` (max 2,147,483,647); the cap stays under it so a valid-looking value can never fail at the column. Zod is the only upper bound (the DB `CHECK` only enforces `>= 0`). |

### Seed data
| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Seed code location | `apps/api/src/seed/`, run with `tsx src/seed/run.ts` via `pnpm db:seed` | `apps/api/prisma/seed.ts` (spec tree) vs. `apps/api/src/seed/` | `tsconfig` only compiles `src/`, so the generator is type-checked, linted and unit-tested with the rest of the API. Prisma's own seed hook isn't used, so nothing depends on Prisma's config-file conventions. |
| Seed determinism | mulberry32 PRNG with a fixed seed; ids are drawn from the same stream (UUID-shaped); hire dates are computed against a fixed reference date (2026-06-30), not `Date.now()` | Random data each run vs. seeded | Two runs produce byte-identical rows, so demos, bookmarks and tests are stable, and no hire date is ever in the future. Cost: the data doesn't age (tenure is "as of 2026-06-30"). Every row consumes the same number of random draws, so the first N rows don't depend on the total count. |
| Seed data model | 9 countries with matching currencies (US, GB, DE, FR, IN, JP, BR, CA, AU); 18 titles with departments and USD bands; band x country cost factor x static approximate USD rate, converted with the ICU minor-unit exponent (JPY 0, others 2) and rounded to 3 significant figures; tenure uplift 1.5% per year (cap 15); part-time 0.6x, contract 1.1x, intern 0.35x (interns only on eligible titles); about 1% deliberate outliers at 1.8x or 0.55x | Uniform random vs. structured | Gives Phase 6 real signal (per-country pay, pay-vs-tenure trend, outliers to detect). The rate table is static and approximate (`APPROXIMATE_USD_RATES` in `packages/shared`, reused by the optional USD view), never fetched. Real seeded salaries top out well under the integer cap (asserted in a test using the worst-case multipliers). Limitation: small name pools mean repeated names; emails stay unique via a numeric suffix. |
| Seed write strategy | One interactive transaction (120 s timeout, default is 5 s): delete all employees, `createMany` in batches of 1,000, verify the stored count equals the generated count, upsert the demo users | Row-by-row upserts vs. delete + `createMany` | All-or-nothing: a failure leaves the previous data instead of an empty table. Only `Employee` rows are deleted; other users and `ApplicationLog` rows are untouched. About 1.3 s for 10,000 rows (3.2 s wall including startup and one bcrypt hash). |
| Demo accounts | Two labelled demo accounts (`hr.demo@acme.example` HR_MANAGER, `viewer.demo@acme.example` VIEWER), same public documented password, overridable with `DEMO_USER_PASSWORD`; role set by the seed itself | One HR user vs. HR + Viewer; password handling | Lets a reviewer try both roles immediately. The password is public by design (it's in the README), so deployed environments should override it. Not validated against the registration password rules; an override is trusted. |
| Seed safety | Refuses when `NODE_ENV=production` unless `ALLOW_PRODUCTION_SEED=true`; `db:reset` runs the same check before it drops anything | Always allowed vs. guarded | The seed deletes every employee; a stray run against a production URL must not do that silently. Seeding a deployed database has to be a deliberate act, hence an explicit opt-in rather than a hard block. `db:reset` wraps `prisma migrate reset --force`, which drops the database; it was not run during this phase (only the guard script and `db:seed` were), so run it once by hand on a throwaway database before relying on it. |

### Screens (React)
The web app is feature-based (`landing`, `auth`, `employees`, `insights`); components hold no API code, and the signed-in pages are lazy loaded.

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Where list state lives | The URL query string (`page`, `search`, `country`, `department`, `jobTitle`, `sortBy`, `sortDir`) | Component state vs. URL | A view can be reloaded, shared and bookmarked and Back steps through it. Invalid values fall back to defaults, and a VIEWER's hand-typed `sortBy=salary` falls back too (the API would answer 400). Changing anything but the page returns to page 1. |
| Debounced search | The URL follows every keystroke (history replaced, so Back is not flooded); only the request waits 300 ms | Debounce the input vs. debounce the request | One source of truth for the input, no state to re-sync when filters are cleared or Back is pressed. |
| Loading | `keepPreviousData`: skeleton only on the first load, then the current rows stay, dimmed and `aria-busy` | Skeleton every time vs. keep old rows | No flashing while paging or filtering. |
| Filter options | The headcount insight (`by=country|department|jobTitle`), open to both roles | New endpoint vs. reuse | No API change; cached 5 minutes. |
| Table vs. cards | A table from `md` up and cards below (both are in the DOM, CSS shows one), plus a sort select for small screens | One responsive table vs. two layouts | A wide table would scroll sideways on a phone; header buttons do not exist on cards. |
| Dialogs | Own modal (`role="dialog"`, `aria-modal`, labelled, focus moved in and trapped, Escape and backdrop close, focus restored) | Native `<dialog>` vs. own modal | jsdom has no `showModal`, so a native dialog could not be tested honestly; the behaviour is identical in every browser and covered by tests. |
| Export | Fetch with the bearer token, then save the blob; the API now exposes `Content-Disposition` and `X-Request-Id` through CORS | Plain link vs. fetch and save | The endpoint needs the token. Without the exposed header a cross-origin browser saves `download.csv`; found in a browser run. |
| Bundle | The signed-in pages are lazy loaded, so Recharts (the dashboard chunk, about 375 KB, 109 KB gzip) is not in the landing or sign-in bundle (about 404 KB, unchanged) | Everything up front vs. on demand | Public pages stay light. |
| Phone filters | Search stays visible; the rest and the sort fold into a "Filters and sort" button with the active-filter count (`aria-expanded`, `aria-controls`); from md up they are always shown | Stacked filters vs. a panel | The first screen of the list is no longer filled with controls. |
| Logout destination | Sign-in page | Home page vs. sign-in page | `ProtectedRoute` moves a signed-out visitor to `/login`; the first version also navigated home, which never won (found by running the app in a browser), so that dead code was removed and the test now asserts the real destination. |

**Design.** The Phase 1 tokens were extended, not bypassed: `ink` (deep blue-black) and `signal` (amber) accents, a serif display stack (no font download), larger type sizes, and shared classes for fields, alerts, radio cards, links and 44 px buttons. The landing page has a dark hero with an illustrative pay-bands graphic built from HTML and Tailwind classes, so text scales and there are no inline styles.

## Auth and roles

Two roles: `HR_MANAGER` (everything) and `VIEWER` (directory and aggregates, no writes, never an individual salary). One sign-in page serves both; login takes an email and a password only, and the API returns the role.

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Password hashing library | `bcryptjs` | Native `bcrypt` vs. `bcryptjs` | Same algorithm and cost factor (12); `bcryptjs` is pure JS with no native addon to compile, removing a class of CI/Docker-image build failures. The measurable cost: hashing takes ~400-600ms in this environment instead of native bcrypt's usual ~50-100ms, which only matters on the register/login hot path, not at rest. Acceptable at this project's scale; would reconsider under real production auth traffic. |
| Login timing-safety | Always compare — against the real hash if the user exists, against a fixed dummy hash (computed once at module load) otherwise | Short-circuit on unknown email vs. always run a password comparison | A `findUserByEmail` miss that skips straight to a 401 is measurably faster than a hit that also runs a ~500ms bcrypt compare, which is itself a user-enumeration side channel via response timing. Comparing against a dummy hash either way keeps both paths' cost dominated by the same bcrypt operation. The dummy hash is computed once per process (top-level `await` in `auth.service.ts`), not per request. |
| JWT revocation / logout | Fully stateless — no `tokenVersion`, no denylist | Add a `tokenVersion` column on `User` (checked on every `authenticate` call) vs. stay fully stateless | Spec §7 explicitly allows this ("implement `tokenVersion` only if it stays small"). A `tokenVersion` check means either a DB read on *every* authenticated request (defeating the point of a stateless JWT) or an in-memory/Redis cache layer (real infrastructure this project doesn't otherwise need). `POST /auth/logout` exists and is `authenticate`-protected for API completeness and to give the client an explicit signal to discard its token, but does nothing server-side. Bounded by the short default `JWT_EXPIRES_IN` (1h). What a real revocation strategy would add later: a `tokenVersion` int on `User`, incremented on logout-all or password change, embedded in the JWT payload and compared against the DB value in `authenticate` — at the cost of a DB read per request, or a cache with its own invalidation problem. |
| `authenticate` and `/me` data source | Trust the JWT payload (`{ sub, role }`) in `authenticate`; only `GET /me` does a `findUserById` lookup, since it's the only endpoint that needs `name`/`email` | Re-fetch the user from the DB on every authenticated request vs. trust the JWT payload | Keeps the JWT payload minimal and `authenticate` fast and DB-free — the actual point of using a stateless JWT instead of a session lookup. Trade-off: a token stays valid (in the sense of passing `authenticate`) even if the underlying user is deleted, until it expires; `/me`'s own lookup catches that specific case (responds 401, not 404, so a deleted user's id isn't distinguishable from a garbage id) but no other route would today. Acceptable for a 1h-lived token at this project's scope. |
| `POST /auth/logout` protection | `authenticate`-protected | Public vs. `authenticate`-protected | Spec only explicitly marks `GET /me` as "(protected)"; logout isn't specified either way. Requiring a valid token to log out matches the general shape of the other protected/unprotected split (you can only log out of a session you're actually in) and costs nothing extra since the endpoint is otherwise a no-op. |
| Rate limiting scope | Two limiters: a global one (`createRateLimiter()`, 300 requests per 15 minutes) in `app.ts`, and a stricter one (10 per 15 minutes) shared by `POST /auth/register` and `POST /auth/login`, built per app | A single global limiter | Registration and login are the obvious brute-force targets. The counters are in memory, so each API instance has its own; behind several instances a shared store (for example Redis) would be needed. |
| Who picks the role at registration | Client may send `role` (`HR_MANAGER` or `VIEWER`), default `VIEWER` when omitted | Server decides (always VIEWER) vs. client chooses from a fixed set | Assessment-only simplification so a reviewer can try both experiences without an admin. It means anyone can make themselves an HR Manager, which a real product must not allow. Production alternative: HR Managers invite Viewers (the invite fixes the role), or new HR Manager accounts need admin approval and self-registration only ever creates a VIEWER. |
| Invalid role input | 400 for an unknown value, a different case, `null`, or any other extra field (schema stays `.strict()`) | Coerce or ignore vs. reject | A typo must never silently produce a different privilege level. |
| DB default for `User.role` | `VIEWER` (own migration) | Keep `HR_MANAGER` vs. `VIEWER` | Registration and the seed pass explicit roles (both demo users), so nothing depends on the default; if a future code path forgets the role it now gets least privilege. |
| Auth router construction | One per `createApp()` (as the app-wide limiter already was) | Module-level router vs. one per app | The register/login limiter (10 per 15 minutes) was shared across every app in a test file, so the role tests hit 429. Each app now has its own counter. |

### Sessions in the browser

**Token storage: localStorage.** The API is a separate origin that takes `Authorization: Bearer` tokens, and the JWT is stateless and short-lived (1 h). The two realistic options are localStorage and an httpOnly cookie:

| | localStorage | httpOnly cookie |
| --- | --- | --- |
| XSS | Injected script can read the token and send it away. The token is valid for at most an hour. | Script cannot read the cookie, but injected script can still make requests as the user while the page is open, so XSS remains serious either way. |
| CSRF | Not exposed: the browser never attaches the token by itself. | Exposed: the browser attaches the cookie to any request to the API, so it needs `SameSite`, a CSRF token or double-submit, and an `Origin` check. |
| Cross-origin API | Works with the current CORS setup. | Needs credentialed CORS, `SameSite=None; Secure` (or the web and API on one site), and new API code to set, clear and rotate the cookie. |
| Effort and blast radius | One small module (`token-storage.ts`). | Changes on the API, the deployment topology and the client. |

Choice: **localStorage**, for a stateless bearer API with no cookie or CSRF machinery, with the XSS risk reduced rather than removed: React escapes output and the app uses no `dangerouslySetInnerHTML`, no third-party scripts, the token expires in an hour, the session is re-validated with `GET /auth/me` on every load, any 401 ends the session, and a strict Content-Security-Policy should be set on the static host at deployment (Phase 10). Roles are also enforced on the server, so a stolen token gives only that user's access. Production alternative: a same-site backend-for-frontend or API issuing an httpOnly, `Secure`, `SameSite=Strict` cookie with refresh-token rotation and a CSRF token. Because all token access is behind `token-storage.ts` (and the HTTP client's token getter), that switch is local.

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Where the role comes from | Ask the server (`GET /auth/me` on load; the login or register response otherwise) | Decode the JWT vs. ask the server | A client-side token can say anything; a test proves a token claiming `HR_MANAGER` still yields the server's `VIEWER`. |
| A 401 | Only when the request carried a token | Log out on any 401 vs. only when a token was sent | A wrong password on login is an ordinary form error; a 401 on a token means the session ended and triggers the auto-logout with an "expired" notice. |
| Server unreachable at load | Keep it, show signed out | Drop the token vs. keep it | A network blip should not sign anyone out; a reload retries. |
| Where a signed-in visitor goes from /login | Back, only for paths inside `/app` | Fixed `/app` vs. back to where they were heading | No open redirect (`//other.example` falls back to `/app`). `PublicOnlyRoute` owns it, because signing in flips the session and a form-level redirect raced it (found by a test). |
| Auth schemas | Moved to `@payscope/shared`, imported as `@payscope/shared/auth` | Duplicate in web vs. share | The client validates with exactly the server's rules, and the subpath keeps the country data in the package root out of the login bundle. |
| Forms | Controlled fields, the shared schemas, TanStack `useMutation` | A form library vs. controlled fields and zod | Two small forms; no new dependency. Errors show on submit and after leaving a field, focus moves to the first invalid field, and server errors map to one place (`form-errors.ts`): 401 generic, 409 inline on the email, 429 and network messages. |
| Account type on register | Radio group, Viewer preselected, helper text for both types and a note that the choice is a demo simplification | Hidden default vs. visible choice | Least privilege by default, as on the server. |

## Role-based data and small-group suppression

The API decides what leaves the server. The service layer takes the caller's role and returns one of two shapes, so a controller cannot receive a raw row. Any role other than exactly `HR_MANAGER` gets the restricted shape (fail closed).

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Where salary is filtered | Service, through one serializer | Controller, repository, UI, or service | Every service function takes the caller's role and returns wire shapes, so a controller cannot receive a raw row. The response types (`EmployeeFull`, `EmployeeDirectory` in `@payscope/types`) differ, so returning the wrong one is a compile error. |
| How the VIEWER shape is built | Explicit allowlist of fields, and an `hrOnly` flag on export columns | Delete `salary` from the row vs. explicit allowlist | A column added to the model later stays hidden from VIEWERs until someone lists it. The directory shape has no `salary` key at all (not null). Any role other than exactly `HR_MANAGER` gets it, so an unexpected value in a token fails closed. |
| Sorting by salary | Reject with 400 on list and export | Allow (order only) vs. reject for VIEWER | A list sorted by salary reveals the ranking even without the numbers. There is no salary filter today (the strict query schema already rejects unknown fields); a future one must be added to `assertQueryAllowed`. |
| What a VIEWER may see | Groups (and salary-band sets) under 5 people are suppressed for a VIEWER, with a count of what was hidden; stats rows for a VIEWER also **omit `min` and `max`** (basic row, allowlisted like the employee shapes; HR gets the full row) | Everything aggregated vs. suppress small groups vs. also drop extremes | The statistics of a group of one are that person's salary, and the minimum and maximum of any group are always one real person's pay. `CLAUDE.md` says "aggregated statistics only"; this closes those holes. One constant and one function (`insights.access.ts`), applied to stats, salary bands and tenure. HR sees everything. See the remaining risk below. |
| Headcount | Not suppressed | Suppress small groups too vs. not | It carries no salary data, so every role sees every group. |
| Hidden groups | Each section that hides groups says "3 groups hidden: fewer than 5 employees"; bands say the selection is too small | One page note vs. per section | The count is specific to what that section shows. |
| Outliers | Omitted for a viewer: not rendered, not requested, no link; for HR it follows the currency and is not converted in the USD view (it says so) | Show and disable vs. omit | Individuals with salaries are HR-only, enforced by the API too. |
| VIEWER layout | The table columns follow the data: a viewer's rows have no `min`/`max`, so those columns are simply not there and no cell is empty | Empty Min/Max columns vs. adapt | No gaps, and nothing to leak by mistake. |
| VIEWER layout | Built without: no salary column or sort option, no actions column, no Add button, and a heading that says salaries are not shown | Disable salary and write controls vs. build without | Matches `CLAUDE.md`: no empty columns or disabled buttons. |

### Viewer salary bands

A VIEWER's salary-band range used to be built from the group's exact minimum and maximum, so the first and last edge were two real salaries (found and recorded after Phases 6 and 8; fixed here).

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Edges | For anyone who is not an HR manager, edges are multiples of one width per currency, never the real minimum or maximum | Data-driven equal bands (HR) vs. fixed edges | The minimum and maximum are individual salaries. The range now reveals a group only to within one step. HR bands are unchanged. |
| Width | About 25,000 US dollars converted with the static rate table and rounded to 1, 2, 2.5 or 5 times a power of ten, in minor units (USD 25,000, GBP 20,000, EUR 25,000, INR 2,000,000, JPY 5,000,000, AUD 50,000; 10,000 major units for a currency with no rate) | One number for every currency vs. per currency | A round step that means the same in each currency, with the currency's own minor unit. |
| Number of bands | The width widens along the same ladder until at most the requested number of bands is needed (checked on the seed: 4 to 8 bands, all edges multiples of the width) | Fixed count vs. at most the requested count | Keeps the chart readable whatever the spread, and the width is a function of a ladder, not of the data. |
| Response | `bucketWidth` is returned, and the UI says "Bands use rounded steps of €15K, so their ends are approximate" | Silent vs. explicit | Nobody mistakes a rounded edge for a real one. |
| What the real min and max do | They only decide how far the edges must reach (`lo = floor(min / width) * width`, and the edge above `max`); they are never returned, and tests search the raw response for every salary in the test data | Use vs. never use | A coincidence (a real salary that happens to be a multiple of the width) reveals nothing, because the edge does not say whether anyone earns exactly that. |

Verified on the seeded 10,000 employees for USD, JPY, GBP and INR: the viewer's bands have 4 to 8 bands, every edge is a multiple of the width, the exact minimum and maximum that HR sees never appear as an edge, and the counts add up to the headcount.

**Remaining VIEWER risk (accepted for now).** With only the under-5 suppression and no extremes, a small visible group (5 to 9 people) can still have a median, quartiles or average that sit close to one person's salary, and someone who can filter to a narrow group (country plus job title plus department) can read them. A band holding one to four people is also still shown: it is a rounded range, not a salary. Tightening options, in order of cost: raise the threshold from 5 to 10 (one constant); round VIEWER money to a coarse step (for example 3 significant figures); or hide bands with fewer than 5 people. The salary-band edges, which used to be the set's exact minimum and maximum, are fixed (see "Viewer salary bands" below).

## Currency handling

Salary is an integer in the currency's minor units. Currencies differ (JPY has no minor unit, KWD has three), so the divisor always comes from the currency itself. Nothing is added or compared across currencies.

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Currencies | Always key **and** currency in the native view | Group by key only vs. key and currency | Never mixes currencies silently. EUR is shared by DE and FR, so by job title they merge into one EUR row, while by country they stay separate. `groupBy=org` (currencies mixed) is only allowed in the USD view. |
| USD view | In SQL: the static rate table goes in as bound arrays, joined as a CTE, using each currency's minor-unit digits (JPY has none) | Convert in JS vs. in SQL | Percentiles must be computed over converted values, not converted afterwards. Results are US cents and labelled `approximate: true`. Employees whose currency has no rate are counted in `excludedHeadcount` instead of dropped silently. |
| Currency | A required selector (named options, most-used first by headcount, a count comparison only); highest and lowest median cards rank countries within that one currency; the employee total is a count | Mixed totals vs. one at a time | Nothing is summed or compared across currencies. The USD view is a separate off-by-default switch with an "Approximate" note and the number of employees with no rate. |
| Money | `minor / 10^fractionDigits` from the currency itself, each row in its own currency, no totals | Divide by 100 vs. per currency | JPY has no minor unit, KWD has three. The form takes major units ("85,000.50"), rejects more decimals than the currency allows, and converts to integers without floating error. |
| ISO country/currency validation | `i18n-iso-countries` for ISO 3166-1 alpha-2, Node's built-in `Intl.supportedValuesOf('currency')` for ISO 4217 | Hand-maintained code lists in `packages/shared` vs. libraries | No list to drift out of date or mistype. Trade-off: the currency list follows the Node/ICU version the process runs on, so a very new or retired code can differ between Node versions; the runtime is pinned to Node 24, so it is stable in practice; a whitelist copy would be the fix if that ever mattered. Both are format-checked (2 vs. 3 uppercase letters) before the lookup. |

## Insights and outlier baseline

Five read-only endpoints under `/api/v1/insights`: `stats`, `headcount`, `salary-bands`, `tenure` and `outliers` (HR only). The dashboard has one query per section, so one failing section never blocks the others.

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Aggregation | Parameterised `$queryRaw` with `percentile_cont` | Prisma `groupBy` plus JS percentiles vs. SQL | Postgres computes quartiles exactly and in one pass; 10,000 rows aggregate in about 10 ms. Values are always bound parameters; the only interpolated fragments are identifiers chosen from a whitelist by key. Counts are cast to `int` and money to `float8` (rounded in JS), so there is no BigInt and no int4 overflow of USD cents. |
| Outliers | Tukey fences (Q1 - 1.5 IQR, Q3 + 1.5 IQR) within `(country, currency, jobTitle, employmentType)`, groups of at least 8 | Fixed percentage from the median vs. a data-driven rule | No magic threshold, adapts to each group's spread, never compares across currencies, and compares like with like: interns, part-timers and contractors are paid differently on purpose. Groups under 8 are never flagged. Group statistics use the whole group; filters only narrow the list. HR only (403 for a VIEWER, before parameter validation), checked again in the service. |
| Tenure clock | The service passes today's date as a parameter | Database `NOW()` vs. a date from the service | Query results do not depend on the database clock. Tests use hire dates relative to today with months of margin around each band edge. |
| Loading | One query per section (country stats, pay by group, bands, tenure, headcount, outliers) | One page-level query vs. one per section | A section that is slow or fails shows its own skeleton or error with retry and never takes the page with it. Keys start with `insights`, so saving an employee refreshes them. |
| Page state | Currency, the USD switch and both chart dimensions in the query string | Component state vs. URL | Shareable and Back works, like the employee list. An unknown currency falls back to the most-used one. |
| Pay chart | Horizontal stacked bars: transparent base to the 25th percentile, then 25th to median (solid) and median to 75th (striped), top 15 by median, axis starting near the data with a note | Box plot vs. stacked bars | Recharts has no box plot; horizontal bars keep long job titles readable at 360 px; a bar shows a range, so a zero-based axis would crush it (the note says so). |
| Text alternatives | Every chart is a `role="img"` with a sentence (also shown) and a "View data as a table" disclosure with a real table outside the image role; series differ by pattern and words, not colour alone; outliers show direction as an arrow, a sign and a word | Alt text only vs. a real table | The numbers stay readable, sortable by eye and screen-reader friendly, and colour is never the only cue. Tooltips are mouse-only, which is why the table exists. |

**Outlier baseline: like-for-like, and the rejected alternative.** The seed injects about 1% deliberate outliers (0.5% at 1.8x, 0.5% at 0.55x). The first build followed the spec literally and compared each employee with the median of their job title within a country, employment types mixed. On the seed that flagged **483** employees (4.8%), including **195 of the 211 interns** (92%), because intern pay is deliberately below the title's median; 69 of the top 100 were interns. That baseline is **rejected**: it mostly reports intended pay differences, not anomalies. Grouping also by employment type flags **176** employees across 233 groups (only groups of 8 or more are judged), and the top 100 are 86 full-time, 9 contract, 4 part-time and 1 intern, with 66 above and 34 below their group's median. The cost is that a group under 8 (for example, few interns in a small country) is never flagged. Measured after the change: 19 ms HTTP for `limit=100` (3 warm runs, was 15 ms) and 14 ms for the query in `EXPLAIN ANALYZE` (a group-by over 10,000 rows and a join; was 27 ms with the earlier plan).

## Logging and error handling

Every request gets an id: a trusted incoming `X-Request-Id` (letters, digits, `_`, `-`, up to 64 characters) or `req_<nanoid>`. It is returned in the `X-Request-Id` header, in every error body and in every log line. All errors go through one global handler that classifies them (`AppError` subclasses, zod errors as 400, Prisma unique violations as 409, other database errors as a generic 500, malformed JSON as 400), logs the full detail, and answers with a safe message only. Sensitive keys (`password`, `passwordHash`, `token`, `authorization`, `cookie`) are redacted once, before any transport sees the entry. Logs go to the console as JSON (pretty in development) and, for `warn` and above by default (`LOG_DB_MIN_LEVEL`), to the `ApplicationLog` table.

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Error handler response sanitization | Always sanitize (every environment) | Branch on `NODE_ENV` (spec's literal "never expose... in production") vs. always sanitize | `classifyError()` already produces a safe `message` for every error, operational or not; branching in the handler to show raw details outside production would duplicate that logic for a marginal dev-convenience benefit. Full detail (message + stack) is always one line away in the structured logs (pino-pretty in non-production), so nothing is lost — just never sent over HTTP, in any environment. Stricter than the spec requires, and simpler. |
| `ApplicationLog` async writes | Fire-and-forget per call | Buffered/batched queue vs. one fire-and-forget write per log call | Spec §10.4 explicitly allows either "a small in-process buffer or batch." At this project's expected local/demo traffic, a batching queue adds real complexity (flush timers, backpressure, partial-batch failure handling) for no measurable benefit. Documented here as the point where a real queue/worker (e.g. a small in-memory ring buffer flushed on an interval, or offloading to a proper queue) would become worth it: once log volume is high enough that per-call `prisma.applicationLog.create()` round-trips start competing with request-serving connections for the pool. |
| Validation error response shape | Single joined `message` string | Add a `details`/`errors` field with per-field issues vs. a single joined `message` | The spec's documented error envelope is exactly `{ success, message, code, requestId }` with no extra field shown for validation errors specifically. `validate()` joins zod's issues into one readable string instead, keeping every error response — validation or otherwise — inside the one documented shape rather than growing an undocumented, validation-only extra field. |
| Retries | Two retries, only for network errors and 5xx | Library default (3) vs. selective | A 4xx will not change, and an error state should appear within seconds. |

## Deployment and hosting

**Layout.** The web app is a static Vite build on Vercel (`apps/web/vercel.json` rewrites every path to `index.html` so deep links work). The API runs on Render from the bundled `apps/api/dist/server.js`. PostgreSQL is a managed database reached through `DATABASE_URL`. The browser calls the API directly; CORS allows only the web app's origin (`CORS_ORIGIN`). Checked on 2026-09-30 from outside: `GET /api/v1/health` on the live API returned 200 with the database up, both public demo accounts could sign in, the live database reported 10,000 employees, a Viewer's employee list had no `salary` key, a Viewer's outliers request returned 403, and the CORS header named the Vercel origin. I did not have access to the Vercel or Render dashboards, so their settings are as the README and these notes describe them, not verified.

**The defect.** `pnpm build` ran `tsc`, which emitted `dist/` but left `@payscope/shared` and `@payscope/types` as imports of their TypeScript source (`"main": "./src/index.ts"`, `.js` specifiers Node cannot map to `.ts`). On Render, `node apps/api/dist/server.js` died with `ERR_MODULE_NOT_FOUND` for `packages/shared/src/roles.js`. `tsx`, Vitest and the integration tests all transpile the source, so nothing caught it.

| Decision | What I chose | Instead of | Why |
| -------- | ------------ | ---------- | --- |
| Fix | Bundle the API with esbuild (`apps/api/scripts/build.mjs`): one ES module for Node 24, workspace packages and the generated Prisma client inlined | Compile `shared` and `types` to JS with `exports` maps (two more build steps and ordering) vs. run `tsx` in production vs. bundle | The smallest change: no new build graph, no dev tool in production, and dev, typecheck and tests are untouched. `tsup` is only a wrapper around esbuild, so the script uses esbuild directly. |
| What stays external | Every real dependency of `apps/api` is external (`express`, `zod`, `pino`, `@prisma/client` and its `runtime/*` subpaths, `@prisma/adapter-pg`, ...) | Everything inlined vs. dependencies external | They resolve from `apps/api/node_modules` at runtime, so Prisma's runtime, the wasm query compiler (a base64 module, no engine file to copy) and `pg` are used exactly as shipped. `i18n-iso-countries`, which only `shared` uses, is inlined. |
| Build script | `prisma generate && node scripts/build.mjs`, deleting any stale `dist/` first | `tsc` vs. generate then bundle | The generated client (git-ignored) must exist before bundling. Turbo hashes `packages/*/src` for `@payscope/api#build`, because inlined code lives outside the package. |
| Repository root | `loadEnvFile` walks up to `pnpm-workspace.yaml` | Count `..` from the file vs. search | The old `../../../..` was right under `src/lib` and wrong inside `dist/`, where it would have looked above the repository. |
| `.env` in production | Never: with `NODE_ENV=production` no env file is read | Read it if present vs. never | Secrets come from the environment only, and it makes the missing-variable check mean something on a machine that has a `.env`. |
| Shutdown | Stop accepting, finish running requests, disconnect Prisma, exit 0; exit 1 after 10 s | Default SIGTERM behaviour vs. graceful | Render sends SIGTERM on every deploy, and the smoke check asserts the exit code. |
| Fail fast | The existing zod config check exits 1 with `Invalid environment configuration:` and one line per bad variable | New check vs. existing | Proven against the production bundle by the smoke check. |

**Smoke check** (`scripts/smoke-production.mjs`, `pnpm smoke:production`): runs the built bundle the way a host does (real environment only, from another working directory) and asserts that (1) with no configuration it exits non-zero naming `DATABASE_URL`, `JWT_SECRET` and `CORS_ORIGIN`; (2) with configuration it answers `GET /api/v1/health` with 200 and the database up (polled every 250 ms for up to 30 s); (3) SIGTERM stops it with exit code 0. Every wait has a timeout, a 90 s watchdog and an exit hook kill the child, and the database name must be a plain name ending in `_test`. It runs in CI after Build and inside `pnpm test:integration` (which always rebuilds first, so a stale `dist` cannot pass). Checked by hand: it also fails, and leaves no process behind, for a non-test database and for an unreachable one.

**Render** (Root Directory empty; verified on a clean clone with `NODE_ENV=production` and no `.env`): environment variables `NODE_VERSION=24`, `NODE_ENV=production`, `DATABASE_URL` (a Neon URL needs `?sslmode=require`), `JWT_SECRET` (32 or more characters) and `CORS_ORIGIN` (the web app's URL); Render sets `PORT`.
- Build Command: `corepack enable && pnpm install --frozen-lockfile --prod=false && pnpm --filter @payscope/api build`
- Start Command: `cd apps/api && ./node_modules/.bin/prisma migrate deploy && node dist/server.js`
- Health Check Path: `/api/v1/health` (200 when the database answers, 503 when it does not)

`--prod=false` keeps the build tools (`prisma`, `esbuild`) installed even if a host omits dev dependencies under `NODE_ENV=production`; on pnpm 12.8.1 a plain install also worked in the clean-clone test, so it is a safeguard, not a workaround. The start command calls the `prisma` binary directly so it needs no pnpm at runtime, and it migrates before the server starts.

**Cold starts.** A Render service on a plan that sleeps when idle can take a while to answer the first request. I did not check which plan is used. Wake the API (open the health URL) before a demo.

## Known limitations and what I would do next

**Not done.**
- **OpenAPI/Swagger docs.** Not built. The API is described in the README table only; `/api/docs` does not exist.
- **Playwright end-to-end tests.** Not written; `tests/e2e/` is an empty scaffold and `pnpm test:e2e` is a no-op.
- **GitHub Actions has not been observed running.** The workflow (type check, lint, format, unit, integration, build, smoke check) matches the commands that pass locally, but I cannot see its results from here.
- **No Content-Security-Policy** on the static host, and no monitoring or alerting.

**Security and privacy.**
- The token is in localStorage, so a script injected into the page could read it (see "Sessions in the browser"). Next step: httpOnly cookie with refresh rotation and a CSRF token, plus a strict CSP.
- Anyone can register as `HR_MANAGER`. It is a demo shortcut. Next step: HR Managers invite Viewers, or an admin approves HR accounts.
- Logout does nothing on the server; a token lives until it expires (1 hour). A `tokenVersion` column would allow revocation at the cost of a read per request.
- The rate-limit counters are in memory per instance.
- A small visible group (5 to 9 people) can still have a median close to one person's salary, and a band holding one to four people is still shown. Options: raise the threshold to 10, round Viewer money, hide small bands.
- `ApplicationLog.userId` exists but nothing fills it yet.

**Product.** No bulk edit, no formatted (major-unit) CSV, no UTF-8 BOM in the CSV, no salary history or audit trail, offset pagination (fine at 10,000 rows, slow at millions), search is a sequential `ILIKE`. On a phone the dashboard is long (25 outlier cards). Chart tooltips need a mouse; the tables are the alternative.

**Testing.** Layout and chart checks were run by hand, not automated. Accessibility was checked for structure, names, contrast, size and focus, not with a screen reader.
